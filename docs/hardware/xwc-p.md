| Platform | Intel Panther Lake — Core Ultra 5 338H, Ultra X7 358H or Ultra X9 388H |
| Profile | [`devices/xwc-p.conf`](../../devices/xwc-p.conf) — **reported** |

Nobody in this repository owns this machine. Everything below is somebody
else's measurement, and each row says whose. There is **no hardware probe of an
XWC-P anywhere** — not on linux-hardware.org, not in the `linuxhw` GitHub
mirrors — so several fields stay `unknown` that one run of
[`tools/collect-hwinfo.sh`](../../tools/collect-hwinfo.sh) would settle.

### The touchpad id is not `27c6:0f9a`

This profile asserted `touchpad_hid=27c6:0f9a` until 2026-08-22. That was wrong,
and it is worth recording why, because the same mistake is easy to repeat.

The value was inferred from the ACPI `_HID` string `TOPS0102`, which XWC-P
shares with the reference ZQC-P. **`TOPS0102` is a slot name, not a part
number.** HONOR uses it on `MRA-XXX` and `MRB-XXX` too, and there the chip
behind it is `35cc:0104`, an entirely different touchpad with its own upstream
`hid-multitouch` quirk. Neither phreer's nor laeo's repository contains a HID
vid:pid anywhere; both were cloned in full and searched.

The field is `unknown` until somebody reads
`ls /sys/bus/hid/devices/` on an XWC-P.

### The touchpad failure, and why this repository's fix applies here

Same defect as the reference machine: the `I2C_DEVT` SSDT contains
`INT1 = GNUM (0x001A088A)` inside `Device (NFC0)`, evaluated at table-load time,
which aborts with `AE_AML_INTERNAL` and takes the whole table down with it.
Confirmed on all four units.

**The table is not merely similar. It is the same table.** phreer published the
full disassembly of their stock `ssdt27.dat`, and against this repository's
[`dump/acpi/zqc-p/SSDT27_orig.dsl`](../../dump/acpi/zqc-p/SSDT27_orig.dsl) it is
identical:

| | XWC-P, phreer, BIOS 1.09 | ZQC-P, this repo, BIOS 1.10 |
|---|---|---|
| length | 23708 | 23708 |
| checksum | `0xE5` | `0xE5` |
| OEM revision | `0x00001000` | `0x00001000` |
| compiler | INTL `0x20200717` | INTL `0x20200717` |
| ASL body | 3862 lines | 3862 lines, `diff` clean |

A 14-inch and a 16-inch laptop, different BIOS versions, one table. That is why
two people arrived at the same one-line fix independently, and it is why
`acpi-override` **is** listed in this model's profile.

The installer does not take that on trust. Before writing anything it finds the
live table by its OEM table id and compares the md5 against the stock table
carried here (`27bb4879…`), and refuses unless they match. Model and BIOS are
printed but do not decide. So on an XWC-P whose firmware has since changed, the
result is a refusal naming both md5s, not a machine that will not boot.

### laeo ships this repository's tables, and that turns out to be fine

Worth recording because it looks alarming and is not. `laeo/Honor-XWC-Linux-Patch`
ships `patch/SSDT27_orig.aml` and `patch/SSDT27_TPD0.aml`, and both are byte
for byte this repository's files:

```
27bb4879b5af49ac2b613a73cf1ffa0b   laeo patch/SSDT27_orig.aml  ==  dump/acpi/zqc-p/SSDT27_orig.aml
0ed8b48df42f797b55714fab5aadaf42   laeo patch/SSDT27_TPD0.aml  ==  patch/acpi-override/SSDT27_TPD0.aml
```

Given that the two machines share the table, shipping ours is not wrong, and
their installer md5-checks the live table against the stock one and refuses
without `FORCE=1` if it differs. The consequence is narrower: **laeo is not a
source of information about XWC-P hardware.** Nothing in it was read off one.
Values in this model's profile cite phreer and the two Manjaro threads instead.

### One thing is still unresolved: replace, or rename

phreer's README carries a bolded warning that keeping the OEM table id
`I2C_DEVT` makes the kernel treat the image as a *replacement*, and that the
replacement path re-executes the module-level code and hits the same bug again.
They rename the id to `I2CDEVC` so it loads as a new table, and ship three
variants: A (`_INI` wrap, as here), B (a fully static `TPD0` with hardcoded
resources), C (the renamed one, which is what their installer uses).

Two people replace with the id intact and it works:

* this repository, OEM revision bumped `0x1000` → `0x2000`. On the machine this
  was written on, `/sys/firmware/acpi/tables/SSDT27` is the patched table and
  the touchpad works.
* [SamenVas](https://github.com/SamenVas/honor-magicbook-pro-zqc-p-linux-fix),
  independently, on a ZQC-P at BIOS 1.09, with the revision bumped to `0x1001`.

Since the stock table is identical on both machines, the disagreement cannot be
about the table's contents. The remaining variable is the OEM revision: the
kernel's `acpi_table_initrd_init()` matches an override on signature, OEM id and
OEM table id, and a table that does not announce itself as newer is easy to
mistake for one that was ignored. Whatever the cause, renaming the id is the
more conservative route and phreer's installer is the one to use if you would
rather not find out. Unresolved.

### The keyboard

Both owners hit it: no events at all from `AT Translated Set 2 keyboard`, fixed
with `i8042.dumbkbd=1`, which one of them now boots with permanently.

**XWC-P is the one HONOR MagicBook missing from the upstream `atkbd` quirk
table.** `FMB-P`, `BCC-N` and `ZQC-P` are all there; adding `XWC-P` is a
three-line patch that would remove the parameter and restore the Caps Lock LED
for everybody with this machine. Nobody has sent it.

One owner also boots with `initcall_blacklist=sysfb_init`. That suppresses the
simple-framebuffer handover, and it may be the same early-display problem
[`patch/cdclk-ptl/`](../../patch/cdclk-ptl/) addresses — unconfirmed.

### The battery limit

A nearly-new unit, three charge cycles, reads back start 40% / end 70% — one of
exactly the three pairs the ZQC-P EC arms. The second unit reads 0/0.

laeo's `battery-limit.sh` defaults to writing `75 80`, which is one of the pairs
this repository has shown the EC stores and ignores. The profile leaves
`battery_charge_presets=unknown` because a `sysfs` readback shows what was
written, not what the EC armed — that distinction is the entire reason
[`patch/battery/`](../../patch/battery/) exists. Settling it takes two commands,
in [TESTING.md](../TESTING.md#4-the-battery-limit).

### Audio is unaffected by the table failure

Worth stating, because it contradicts one report on the reference machine.
Both pre-fix `inxi` dumps show `sof-audio-pci-intel-ptl` bound and PipeWire
running while `I2C_DEVT` is failing to load. On XWC-P the audio path does not
go through that table. See [zqc-p.md](zqc-p.md#the-speakers-disagreement) for
why it does on some ZQC-P units.

## Not established

`touchpad_hid`, `audio_ssid`, `backlight_max`, `ec_fan0`, `ec_fan1`,
`battery_charge_presets`. Both `inxi` dumps read `Fan Speeds (rpm): N/A`, and
only the `I2C_DEVT` SSDT was ever published for this machine — it contains no
EC region, so the tachometer offsets cannot be recovered from it.

One run each of [`tools/collect-hwinfo.sh`](../../tools/collect-hwinfo.sh) and
[`tools/dump-acpi.sh`](../../tools/dump-acpi.sh) would close all six.
